凭据管理与顾客验证 —— 两条线的方案对比

左半篇解决「怎么让 AI 自动推送、又不在磁盘上留明文口令」；右半篇解决「顾客凭什么算登录， OTP 到底走哪条通道」。每项都给可选方案、代价、和我建议的落点。

2026-09-26 状态：待你选定后再开发

零先看清今天这两个洞

洞一 · 推送凭据是「账号级明文」。 现在那份 PAT 是 classic 类型、带 repo 权限，意思是它能读写你 GitHub 账号下的 全部仓库，还能改其它仓库的协作设置。它以明文躺在 .workbuddy/memory/MEMORY.md 里 —— 该目录已被 gitignore，不会进公开仓库，但 任何能读这个文件的程序/人就等于拿到了你账号的这把万能钥匙，而且它没有到期日，只能你去手动撤销。

洞二 · 顾客身份是客户端自己填的。 src/lib/auth.ts 第 15 行读的是请求头 x-user-id，而那是前端自己塞的。 上一轮我把查询串和请求头做了一致性校验，但那只是把门锁在门框上： 只要知道别人的 id，照样能以别人名义下单、看别人订单、改别人资料。 真正的修法只有一个 —— 给顾客一个只有本人能完成的验证步骤。

壹推送凭据：AI 能自动推，明文不出你电脑

本机实测：GitHub Desktop 3.5.6 自带 git-credential-manager.exe，Windows 也有 OpenSSH 10.3 —— 四个方案都不用额外装东西。

方案 ① · 交给 Windows 凭据管理器（GCM）推荐

原理：让 git 用 GitHub Desktop 自带的 Git Credential Manager 当凭据助手。 token 交给 Windows 凭据管理器保管，底层是 DPAPI 加密，只有你当前这个 Windows 账户能解开。 AI 之后只是执行 git push，凭据由助手在后台提供。

好处

  • 磁盘上不再有任何明文：不需要 token 文件，仓库里、内存转储里都没有可读口令
  • AI 完全自动化：首次授权一次，之后推送零交互
  • 零额外安装：GCM 就在 GitHubDesktop/app-3.5.6/resources/app/git/mingw64/bin/
  • 换钥匙便宜：token 作废后重新授权一次即可，不用改任何文件

代价与注意

  • 首次要你手动点一次浏览器授权（GitHub 的 device flow）
  • 路径里带版本号 app-3.5.6，GitHub Desktop 升级后会失效 → 要把 GCM 复制到一个固定目录，或让配置指向稳定副本
  • 它只解决「明文」问题，不解决「权限过大」 → 建议同时把凭据换成只授权本仓库的 fine-grained token
  • 凭据是按 Windows 账户隔离的，换电脑/换账户要重新授权

方案 ② · SSH Deploy Key（只挂这一个仓库）推荐

原理：本机生成一对 ed25519 密钥，公钥作为 Deploy Key 并勾选「允许写入」只挂到 cdh428/hook-fishpond 这一个仓库上，私钥留在 %USERPROFILE%\.ssh\。remote 从 https 换成 SSH。

好处

  • 作用域最窄：这把钥匙只能推这一个仓库。就算泄漏，也碰不到你账号下的其它仓库和账号设置
  • 不存在「明文口令」这个概念：私钥是文件不是可粘贴的字符串；还能加 passphrase 再上一道锁
  • 不会过期：fine-grained PAT 最长一年，到期就断；Deploy Key 不用管续期
  • AI 直接 git push，无凭据交互、无浏览器跳转

代价与注意

  • 只对这一个仓库有效（将来加新仓库要再加一把）
  • 私钥文件本身要防丢：丢了到 GitHub 撤掉重加一次即可，但要有这个动作
  • 要改 remote 地址；.gitignore 得补上私钥文件名，避免哪天误提交

方案 ③ · 本地加密文件 + 推送脚本

原理：token 用 DPAPI 加密后存到 .workbuddy/secrets/pat.dpapi（同样 gitignore）。 写一个 scripts/push.mjs：运行 → 在内存里解密 → 设一次性的 GIT_ASKPASS → 调 git push。

  • 明文只在内存里出现一瞬，落盘的是密文
  • 不依赖 GCM 的安装位置，升级 GitHub Desktop 不受影响
  • 多一层要自己维护的脚本（GCM 是别人维护的成熟件）
  • 收益与方案 ① 基本重合，但复杂度更高

方案 ④ · 维持现状，只加「防泄漏闸门」

明文继续留本地，但补一条 git pre-commit 钩子：提交内容里命中 ghp_ / github_pat_ / sk- / BEGIN … PRIVATE KEY / 管理员口令模式就直接拒绝提交。

  • 改动最小，能拦住「哪天手滑把 .workbuddy 加进暂存区」这类事故
  • 不解决明文本身：只是加了一道保险，磁盘上那串字还在
建议：无论如何都把这条闸门加上 —— 它是①②③任一方案的兜底，成本几乎为零。

管理员口令轮换（和上面独立的一件事）

轮换不该经过聊天窗口，也不该进仓库或 Vercel 环境变量（服务端只需要比对 hash，不需要知道原口令）。做法：

本地生成强口令→ 只写入 .workbuddy/secrets/admin.local.env→ scripts/rotate-admin-password.mjs 读取→ bcrypt 后 UPDATE AdminUser
  • 明文全程只存在于你本机那个 gitignore 文件里，聊天记录、git 历史、Vercel 都没有
  • 轮换后旧口令立即失效；顺手换一次 ADMIN_SESSION_SECRET 还能一次性踢掉所有已登录会话
  • 要提醒店员：换了之后收银台那边要用新口令登录

四条路横向对比

方案明文落盘权限范围过期AI 免交互维护成本
① GCM无看你发的 token看 token是低
② Deploy Key无（私钥文件）仅本仓库不失效是低
③ 加密文件+脚本无（密文）看你发的 token看 token是中
④ 现状+闸门有账号全部仓库手动撤销是最低

我的建议：② Deploy Key 为主 + ④ 的防泄漏闸门。 理由：Deploy Key 是唯一一个同时做到「作用域锁死在一个仓库」「不会到期」「没有可复制粘贴的明文口令」的选项， 而这三点正好覆盖你今天的顾虑。将来如果要接别的仓库再单独加钥匙即可。 如果你更想保留 PAT 的形态，那就选 ①，并把 classic 换成只授权本仓库的 fine-grained token。

贰顾客验证：OTP 走哪条通道

目标不是「加个验证码框」，而是把顾客身份从「客户端自称」换成「本人能证明」。成本按每天约 40 位客人、人均 1.5 次验证 ≈ 每月 1,800 次估算。

方案 A · LINE Login（一键授权，不做验证码）推荐主路

原理：在 LINE Developers 建一个 LINE Login channel（免费），网站上放一个 「用 LINE 继续」按钮，跳转授权后拿回 LINE userId + 昵称 + 头像。 这个 userId 由 LINE 签发且绑定了 LINE 账号 —— 身份立刻变成不可伪造。

点「用 LINE 继续」→ LINE 授权页→ 回调带 code→ 服务端换 userId→ 建/找 User，发签名会话

好处

  • 成本 0：没有按条计费这件事
  • 泰国覆盖率最高，顾客手机上基本都装着，一步点完，比等短信舒服
  • 顺带解决「忘记手机号 / 换号」的账号找回问题
  • 能给以后做会员、推播打好底子

代价与注意

  • 拿不到手机号：LINE Login 默认只给 userId / 昵称 / 头像。要手机号是另一码事 —— 需要申请 OC_PHONE_NUMBER 权限，前置条件是 LINE Certified Provider （据 LINE 规范只开放给公司/商行/商号，个人与农场、财团法人不能申请）+ OA 必须是蓝盾或绿盾认证账号。 这是一条要走审核、可能还要花认证费的路，别把它当成免费赠品
  • 没有 LINE 的顾客（部分外国客人）进不来 → 必须配兜底
  • 需要你在 LINE Developers 后台建 channel，生效约 2 小时
  • User.phone 目前是必填且唯一，改成 LINE 登录后要么放开为可空，要么在授权后单独请他补填手机号（此时手机号只是联系方式，不再是身份）

方案 B · 短信验证码 · ThaiBulkSMS推荐兜底

原理：泰国本地短信平台，REST API v2（api-v2.thaibulksms.com）， 直连泰国运营商、过 PDPA，自身也卖 OTP 产品。

单价低至 ฿0.15/条
每月估算1,800 条 ≈ ฿270/月
开通门槛注册企业账号 + 报备发送者名称（需审核，通常几天）
要自己写的验证码生成 / 存储 / 失效 / 重试 / 限流
  • 最便宜，比 Twilio 便宜近一个数量级
  • 泰国本地落地，送达率与合规性都更稳
  • 限流逻辑不用从零写：项目里已有 src/lib/rate-limit.ts 可直接复用
  • 发送者名称报备要等审核，不能今天注册今天就发
  • 验证码的存储/失效/重试要自己实现（约一个数据模型 + 两条接口）
  • 要管理余额，欠费会静默失败 → 需要加余额告警

方案 C · 短信验证码 · Twilio Verify（省事但很贵）

原理：托管式验证服务 —— 验证码生成、重试策略、防欺诈（Fraud Guard）全包， 你只调两个接口（发起 / 校验）。

单价$0.05/次验证 + 泰国短信 $0.0305/条 ≈ $0.08/次
每月估算1,800 次 ≈ $144 ≈ ฿5,000/月
开通门槛注册即用，最快
要自己写的几乎没有
  • 集成最快，且内置防刷（对短信轰炸/薅流量这种攻击有现成防护）
  • 不用自己管发送者名称报备和运营商规则
  • 比方案 B 贵约 20 倍，对一间鱼塘的体量来说不成比例
  • 按次计费意味着被刷就是直接烧钱

方案 D · 用现有 LINE 官方账号收码（免费，摩擦大）顺手可得

原理：你已经有 OA @300bsham、已经写好的 webhook（/api/webhooks/line）， 以及 src/lib/line.ts 里的 replyLineText。 流程：网页发起验证 → 引导顾客到 LINE 给官方账号发一条消息 → webhook 收到他的 userId → 绑定到这次登录。

关键便宜点：LINE 的回复消息不占推送配额、也不计费（主动推送才计费）。 这条链路上官方账号只做「回复」，所以消息成本是 0。
  • 完全免费，且不用新开任何账号
  • 能证明「这个人控制着那个 LINE 账号」，安全强度足够替代 x-user-id
  • 附带营销资产：顾客为了收码必须加官方账号为好友 → 你多一个可推新品/活动的触达位
  • 摩擦明显大于短信：要切到 LINE、搜索/点开官方账号、发一条消息，再切回来
  • 只能证明 LINE 账号，不能证明手机号
  • 需要把 webhook 从「只给管理员推日报」扩展成「也处理顾客绑定请求」

方案 E · 混合：LINE Login 主 + 短信兜底我建议的落点

顾客类型走哪条单次成本步骤数
有 LINE（泰国绝大多数）A · LINE Login฿02 步
没有 LINE / 外国客人B · SMS 验证码฿0.153 步

覆盖面最大、成本最低。代价是工作量约为单做一条的 1.6 倍 —— 两套回调都要写， 但身份模型是同一套（User 上多两个可空唯一列 lineUserId / 手机号验证标记），不是两套并行系统。

落地改动清单（估）

  • 数据层：User.phone 放开为可空 + 新增 lineUserId 唯一列 + 验证码表（方案 B 才需要）
  • 服务端：/api/auth/line/start|callback、/api/auth/otp/send|verify
  • 会话：把顾客会话也换成和后台同款的 HMAC 签名 cookie（auth.ts 里已有现成实现，扩展一下即可）
  • 前端：登录/注册页加「用 LINE 继续」+「用手机号」两个入口；AppContext 不再往请求头塞 userId
  • 三语文案 + 三语核验（这是固定检查项）

方案 F · 我看过但不建议的两条

Firebase Phone Auth不推荐

  • Firebase 官方电话验证价格表里没有列出泰国，覆盖取决于运营商支持 → 在泰国能不能稳定发码有不确定性
  • 正式环境必须挂 Blaze 计费账户；单价 $0.01–0.06/次，也不比 ThaiBulkSMS 便宜
  • 会把身份体系从 Prisma/Neon 分叉到 Google 那边去，多一套要维护的真相

Supabase Auth Phone不推荐

  • 你的 Supabase 项目现在是冷备库，用它做认证等于又造一个身份来源
  • 它背后同样是转手 Twilio / Vonage，费用不会更低，只是把复杂度换个地方

我的建议：方案 E（A 主 + B 兜底）。 泰国客人基本都装着 LINE，主路免费又最顺；少数没 LINE 的走短信，฿0.15 一条， 按你的客流一个月两三百泰铢，比一次维修费都低。 如果只想先做一版验证概念，那就先只做 A —— 它零成本、零开户等待， 能独立把「身份可伪造」这个问题修掉，短信随时可以后补。

一条共通的前置提醒：方案 A 需要你在 LINE Developers 建 LINE Login channel； 方案 B 需要注册 ThaiBulkSMS 并报备发送者名称（要审核几天）。这两件事 都得你本人去办，我这边做不了。所以真正该先定的不是代码，而是「要不要现在就去开户」。
