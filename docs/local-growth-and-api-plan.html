四条线一步步做：Google 商家 / LINE Messaging / OTP / Meta

四条线不是四件并列的事，它们是一条链：Google 让人找到你 → LINE 把人留住 → OTP 让你认识他 → Meta 把内容传出去。 下面每条线都拆成「你点哪里、填什么」＋「我写什么代码」两栏，你只要照着把红色标签的步骤做完， 剩下的交给我。

先说三个能帮你省时间的结论（都是这次核实平台规则时发现的）：

  • LINE Messaging API 的代码我们已经写完了。webhook、验签、自动绑定接收人、日报推送 —— 全在仓库里。 你缺的只是「在 LINE 侧把渠道打开 + 填 3 个环境变量」，今天就能跑通，不用等我开发。
  • Google 商家资料的 API 有个 60 天硬门槛：必须「已验证且活跃满 60 天」才能申请。 所以认领验证这件事越早做越好，而且它完全不依赖我和其他人 —— 今天就能开始。
  • Meta 那条线对你这门生意性价比最低。发一条 FB/IG 帖文，手机上手点 30 秒；为了自动化它去走 App Review ＋企业认证，可能要等 2–6 周。建议排最后、而且第一期只做一个接口（详见第柒节）。

情形 D 专章：同一个塘，Google 上有两个资料

先搞清 Google 的机制，这决定了你每一步该做什么：

  • Google 不会把两个资料「合成一个」。它只会判定其中一个不该存在， 把那个从搜索和地图上撤掉，把信息与评论并到留下的那个上。
  • 官方说法：评论会合并，但「对评论的回复」可能丢失。 实测统计约 95% 的已批准合并会迁移评论。
  • ❗被撤掉那个上「你自己发的内容」会永久消失 —— 动态、你上传的照片/视频、你对评论的回复。 顾客写的评论会留下。这一条决定「该保留哪一个」。

第 2 步：先把 NAP 对齐（这步不能跳）

NAP ＝ 名称 / 地址 / 电话。Google 的自动系统只认三项一致的「明显重复」。 所以顺序是：

  1. 先确定要保留哪一个。判断标准按优先级： ① 谁是你真的在做生意的地方（地址对的优先）； ② 谁上面有你自己发过的内容（动辄几十条动态、几百张照片的话，保留它更省事）； ③ 谁的评论多。（评论能迁移，所以这条优先级最低。）
  2. 把要淘汰的那个的信息改成和保留的那个一致 —— 在它页面上点 「建议修改」→「更改名称或其他详细信息」，把名称/地址/电话改成正确的，等审核通过。
    ⚠️ 如果它已被别人认领，你改不动 → 直接跳到第 3 步的「已被别人认领」那一行。
  3. 三项一致之后，才进入第 3 步报重复。

第 4 步：留底，然后等

提交前两个资料的评论数、照片数都截图存好。合并一般 3 天～6 周（多数两周左右）。 万一评论真的丢了，那张截图是你申诉时唯一的依据。

第 5 步：根因是「名字有三个版本」，这个必须一起收口

现在三个地方的名字不一致： Google 上是 Hook the Happyness（多一个 the）、 Facebook 主页是 Hookhappyness、 网站品牌是 Hook Happyness。 名字不一致本身就是重复资料的成因之一（Google 从多个数据源抓信息，抓出两个不同名字就会当成两个商家）。 所以合并完必须顺手统一，否则过一阵还会再长出第三个。

我的建议：官方名统一成 Hook Happyness（与网站、FB 主页一致）； 泰文名 ฮุค เดอะ แฮปปี้เนส 作为泰文搜索的别名处理 —— 写在商家描述里、并让网站泰文版和地图定位链接都用它。 前提是：这个名字在实体的招牌/门头上也是这么写的（Google 的命名规则要求与现实一致， 不一致会改名失败甚至被判违规）。这件事我需要你确认实体招牌上写的是什么。

另外提醒一句：不管最后保留哪个名字， 「认领 + 验证」应该做在地址正确的那个上（也就是你现在搜泰文名找到的那个）。 别先花力气去认领那个地址错的 —— 验证要现场录视频，地址不对会直接卡住。

第 1 步：认领 / 新建 需你操作

  1. 用哪个 Google 账号？用钓场以后长期持有的那个，不要用个人小号。 这个账号会被记为该商家的所有者，以后所有验证、转账、API 申请都要用它。
  2. Google 地图搜店名 → 找到就点「认领此商家」 → 「立即管理」；找不到就去 business.google.com/add。店名建议填 Hook Happyness（和 FB 主页一致）， 中文「乐钓鱼塘」可作为别名 —— 但不要在店名里堆关键词（会被判违规改名）。
  3. 填地址时：如果客人真的会开车到这里吃鱼、钓鱼，就填真实门牌，让地址公开显示； 如果你不想公布门牌（比如塘在自家院内），就选「服务区域商家」并画服务范围 —— 这个选择在验证前定好，中途改会触发重新验证。这一步你先判断，我按你的选择调网站上的文案。

先给一个坦率的判断。你的生意是「客人开车来、坐一下午」的本地生意。 FB/IG 的价值在于作为一个内容资产被人看到（这件事人工发就够，而且效果一样）， 而不是「自动化发帖」这个技术能力本身。 为了自动化去走 App Review ＋企业认证，可能要等 2–6 周、提交资料、还可能被拒一次 —— 这段时间的投入产出比，比把 Google 商家资料填满、把 LINE 日报跑起来都低得多。

第 1 步：账号前置 需你操作 20 分钟

  1. IG 必须是「专业账号」。IG 设置 → 账号类型和工具 → 切换为商家或创作者账号。 个人账号在 API 上是完全被封死的，不管代码怎么写都发不出去。
  2. IG 必须绑定一个 Facebook 主页。这是最常被漏掉的一步 —— 因为 Meta 的权限体系是 绕着脸书主页走的，哪怕你根本不打算发 FB 也要绑。没有主页就先去建一个（两分钟，不需要发内容）。
  3. 把 IG 和 FB 主页的名称、简介、营业时间、电话、网站都改成和 Google 商家资料一致。 三个地方信息不一致，客人会怀疑，Google 也会降低信任度。

第 2 步：建 Meta App 并拿长期令牌 需你操作

  1. developers.facebook.com → 新建 App → 类型必须选 Business → 添加 Instagram Graph API 产品。
  2. 需要的权限（一次全勾上，事后补权限要重新走一遍授权）：
    权限用途
    instagram_business_basic读 IG 资料（发帖必需）
    instagram_business_content_publish发 IG 帖
    pages_manage_posts发 FB 主页帖
    pages_read_engagement读主页信息
    instagram_manage_comments发首条评论（想用话题标签就加）
  3. 拿长期令牌。先用 Graph API Explorer 拿短期 token，再换成长期： 
    GET https://graph.facebook.com/v23.0/oauth/access_token
    ?grant_type=fb_exchange_token
    &client_id=<APP_ID>
    &client_secret=<APP_SECRET>
    &fb_exchange_token=<短期令牌>

这条线最容易翻车的地方就在这里：长期令牌 60 天会过期。 如果不管它，表现不是报错，而是「某一天开始悄悄不发帖了」 —— 你根本不会发现。 所以必须配一个自动刷新： 
GET https://graph.facebook.com/v23.0/oauth/access_token
    ?grant_type=fb_exchange_token
    &client_secret=<APP_SECRET>
    &fb_exchange_token=<当前的长期令牌>
我会把它挂到你已有的 Vercel Cron 上（你已经有 daily-report 和 stock-sweep 两个定时任务）， 每 45 天刷新一次并写回数据库，同时在刷新失败时给管理员推一条 LINE 提醒。 这件事不做，整个自动化就是「一个月后无声失效」。
