# 餐饮 / 零售收银台财务口径（Hook Fishpond 落地版）

> 由金融 skill 通用财务原则蒸馏而成，**只保留对「现场收银 + 后结算」真正用得上、且能写进代码的部分**。
> 股票 / 估值 / 行情类方法论一律不适用，本文件不涉及。

## 一、记账原子性（最核心一条）

**收款流水必须是独立、不可变、可追溯的原子事件，不能是订单上的一个覆盖字段。**

- `order.prepaidAmount` 是一个**汇总数（存量）**，只适合「快速显示需付」；
  **绝不能用它当账**——它无法回答「几点、谁、用什么方式、收了多少」。
- 账必须是流水表：`orderId + amount + method + operator + paidAt + note`，**只追加不修改**。
- 一笔订单可以有 **N 条**付款流水（多次点单、多次付款、分次补款），
  N 条之和 = 该单实收。**这是对账的唯一真相来源（single source of truth）**。

### 代码落点
- 表：`PaymentRecord`（orderId, amount, method, operator, paidAt, kind, note, voidedAt）
- `kind`：`DEPOSIT`（定金/预付） / `PARTIAL`（中途补款） / `FINAL`（结清补差） / `REFUND`（退现，负数）
- 显示用的 `prepaidAmount` 改为**流水求和派生**，不再独立维护（避免两套数打架）。

## 二、两个口径必须分开说

| 口径 | 定义 | 用途 |
|---|---|---|
| **应收（billed）** | 订单当前总应付 `totalPrice`（菜品 + 渔获 + 服务费 − 折扣） | 客人该付多少 |
| **实收（collected）** | Σ 有效付款流水 | 钱箱里有多少 |
| **需付（outstanding）** | `max(0, 应收 − 实收)` | 还差多少 |
| **多收（overpay）** | `max(0, 实收 − 应收)` | 该退多少 |

**铁律**：
- 需付按 `max(0, …)` 封顶，**不出现负数欠款**；
- 多收**单列**为「需退」，不能混进收入；
- 结清时**以实收为准**入账，不以「结清动作发生」为准。没收到钱就结清 = 账实不符。

## 三、收入确认时点（餐饮后付场景）

- **权责发生时点**：出餐/上菜（`SERVED`）——收入在此时"赚到"，但钱可能还没到手。
- **现金实现时点**：每笔 `PaymentRecord.paidAt` —— 钱箱在这时变化。
- **日报/营业收入**按哪个？→ **按流水实现制**（`paidAt` 落在哪一天算哪天），因为
  跨天营业（客人昨晚吃、今天结）时，按 `createdAt` 会**今天收的钱记到昨天**，账实不符。
- 所以：**营业收入 = 当日全部有效流水之和**，而不是当日 `SETTLED` 订单的 `totalPrice` 之和。
  两者差额 = 应收未收（挂在未结清单上）。

> ✅ **已落地（2026-10-25）**：`src/lib/reports.ts` 的 `fetchPeriodRevenue` / `fetchTrend`
> 已全部改为实收现金流口径 —— 营收趋势/报表的「营收」按 `PaymentRecord.paidAt` 落日，
> 毛利随营收口径（实收 − 成本）。导出的 summary 表、仪表盘「今日进账」三者同口径。
> ⚠️ 单品毛利（`fetchItemStats`）仍按订单销量口径（按菜品归属，不随现金流），二者有意分开。

## 四、对账三张表（每天收工必跑）

1. **收款流水表（按时间倒序）**——谁在几点收了多少钱，方式是现金还是扫码。
   这是收银员的"操作日志"，也是纠纷时的凭证。
2. **未结清台账（按订单时间正序）**——每单：应收 / 实收 / 需付 / 最后一次变动时间。
   时间正序才能看出「哪单最老最久没动」，是催收顺序。
3. **长短款差异表**——现金应收（Σ CASH 流水）vs 钱箱实点。差多少、差在哪单。

## 五、订单内多次点单 / 多次付款的展示规则

用户明确提出：**按订单变更时间排列更新**。

- 每张订单记录 `lastActivityAt`（取 `updatedAt`、最近一条流水 `paidAt`、最近一条菜行 `createdAt` 三者最大值）。
- 后端 `orderBy: lastActivityAt desc` —— **最近有动作的单浮到最上**，
  顾客又加了一道菜、或店员记了一笔定金，这张单立刻跳到顶部，不会被压在老单里。
- 订单卡片内：菜行按 `createdAt asc`（先点的在上，看得出追加顺序）；
  **付款流水按 `paidAt asc`（时间正序，像账本一样从早到晚读）**。
- **两种排序方向是故意的，不要统一**：
  列表用**倒序**（找最近的动作），单据内流水用**正序**（当账本读）。混用会让人读错时间轴。

## 六、防呆（这些错误在收银现场一定会发生）

| 错误 | 后果 | 防呆做法 |
|---|---|---|
| 重复记同一笔定金 | 实收虚高，多退钱 | 同单同额同方式 5 分钟内重复 → 二次确认 |
| 记的金额超过总应付 | 需付变负 | 拒记，提示「最多可再记 ฿X」，多出部分走退款流水 |
| 已结清的单再记一笔 | 结清后账还在变 | 结清后流水只允许 `REFUND` |
| 退货/退菜后没冲流水 | 应收降了实收没降 | 退菜必须同步重算 `totalPrice`，并显式提示是否退款 |
| 两人同时操作同一单 | 覆盖写 | 流水只追加不覆盖，天然免疫；汇总数改成派生 |

## 七、不能做的事（红线）

- **不得把「结清」当成「收到钱」**：结清只改状态，钱靠流水记。
- **不得在流水上做 update 覆盖**：要更正就追加一条冲销（负数）或标 `voidedAt`。
- **不得把退款记成负数收入混在收入里做合计**：退款单列，净收 = 实收 − 退款。
- **不得按订单 `createdAt` 汇总当日营业额**（跨天单会错）。
- **不得用浮点数之外的方式存金额时做四舍五入到 0.01 以外的精度**：泰国泰铢流通最小单位是 0.25 铢（硬币），
  但扫码金额按 0.01 精度没问题；**现金收款建议提示自动按 1 铢取整**，避免找零麻烦。
