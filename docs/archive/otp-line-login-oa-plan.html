OTP 方案 ②+④ —— 全 LINE 通道，零短信成本

只用你手上已有的资产（LINE 官方账号 @300bsham + 现成的 Messaging API）， 把顾客身份从「客户端自称」换成「LINE 签发的身份」。不接短信、不产生按条费用。

先说一个能省掉一半工作量的发现： ② 和 ④ 不需要做成两套并行系统。LINE Login 的授权链接支持一个参数 bot_prompt=aggressive —— 用户点「用 LINE 继续」时，LINE 的授权页会 顺便问他要不要加你的官方账号为好友。也就是说 「登录成功」和「成为官方账号好友」在同一步里完成， 而后者正是 ④ 最大的附加价值。

壹为什么 ④ 还值得单独留一条兜底

既然登录顺带就加了好友，④ 还剩什么用？两个真实场景：

  • 客人已经在 LINE 里跟你说话了。他正在官方账号里问「今天有位置吗」， 这时让他跳出去网页再点一次授权，是多余的。④ 允许他直接在聊天窗口里完成识别 —— 他发一句几个字符的短码，网页那边就认出来了。
  • 浏览器侧走不通时。LINE 内的应用内浏览器对第三方授权跳转偶有拦截； ④ 不依赖浏览器跳转，只要他能在 LINE 里发一条消息。

而且 ④ 用的 replyLineText 是 回复消息 —— 免费且不占官方账号的推送配额 （你项目里已经实现了）。所以这条兜底的边际成本是 0。

贰② 主通道：LINE Login 完整流程

点「用 LINE 继续」→ 授权页（此处显示"加官方账号为好友"）→ 回跳带 code→ 服务端换 access token→ 取 userId + 昵称 + 头像→ 建/找 User，发签名会话

关键点：userId 由 LINE 签发、不可伪造、不可枚举。 这一个值取代今天那个「客户端自己填的 x-user-id」，越权问题从根上消失。

顺带还能查一件事：GET /api.line.me/friendship/v1/status （带上登录拿到的 token）能告诉你他到底加没加官方账号好友。没加的话可以温和提示 「加了才能收到订单进度通知」，而不是硬拦。

叁④ 兜底：在聊天窗口里完成识别

网页生成 6 位一次性短码→ 深链跳到 LINE 聊天窗→ 客人发送该短码→ webhook 收到 userId + 短码→ 回复确认（免费）→ 网页轮询到结果，发会话

深链格式：https://line.me/R/oaMessage/@300bsham/?<短码> —— 点开就自动跳到与官方账号的对话并预填内容，客人只需按发送。

安全上要注意什么（我按这个设计）：短码 6 位、5 分钟失效、一次用完即废， 并且与发起那个浏览器的一次性票据绑定。这样即使短码被别人看到并抢先发送， 结果也只是「他自己的 LINE 被绑到你的浏览器会话上」，不会导致你的账号被夺走 —— 因为最终发会话的对象是持有票据的那个浏览器。

肆只有你能办的三件事 需你操作

这三件我替代不了，也是整件事的唯一卡点。代码我可以先写好，但没有它们跑不起来。

1. 在 LINE Developers 新建一个 LINE Login channel

  • ⚠️ 必须放在「现有的那同一个 Provider」下面 —— 就是承载消息推送的那一个。 LINE 的 userId 是按 Provider 维度签发的，跨 Provider 就对不上号； 而且 channel 建好之后不能迁移到别的 Provider。这一条最容易被忽略，也最难补救。
  • Callback URL 填两个：
    https://hookfishpond.com/api/auth/line/callback
    http://127.0.0.1:3100/api/auth/line/callback（本地调试用）
  • 把 OpenID Connect 打开（需要它才能拿 ID token）
  • 把 Linked LINE Official Account 指到 @300bsham 那个 Messaging API channel —— 这一步不做，bot_prompt 就不生效，「登录顺便加好友」就没了
  • Privacy Policy URL 通常要填才能正常上线

2. 把两把新钥匙放到 Vercel 环境变量：LINE_LOGIN_CHANNEL_ID、 LINE_LOGIN_CHANNEL_SECRET（LINE_CHANNEL_ACCESS_TOKEN 你已经有，直接复用）
3. 等 channel 生效（约 2 小时）后告诉我一声，我这边就能端到端跑通并上线。

陆必须说清的三条限制

  • 拿不到手机号。LINE Login 默认只给 userId / 昵称 / 头像。想要手机号需要 OC_PHONE_NUMBER 权限，前置是 LINE Certified Provider （据 LINE 规范只开放给公司/商行/商号）+ 官方账号蓝盾或绿盾。 这是一条要走审核、可能还要花认证费的路，这次不做。 所以「顾客手机号」以后只是他自愿填的联系方式，不再是身份凭证。
  • 没有 LINE 的客人进不来。泰国覆盖率极高，但外国客人存在。 这正是当初「混合方案」要留短信的原因 —— 短信可以以后随时补上，接口是独立的，不会推翻这次的结构。
  • 先有 channel 才能验证。在那之前我写出的登录代码无法端到端测试， 所以顺序是：你先建 channel → 我写 + 本地跑通 → 上线。

柒验收标准（我上线前会逐条跑）

  • 本地 3100：走通一次「用 LINE 继续」，拿到会话；数据库里出现带 lineUserId 的 User
  • 反例：伪造会话 cookie → 401；不带会话访问 /api/orders → 401； 用 A 的会话查 B 的订单 → 403（取代今天「改个头就能读」的状态）
  • 短码路径：生成短码 → 在测试账号里发送 → 网页轮询拿到会话；同一短码第二次使用应失败； 5 分钟后使用应失败
  • 三语核验通过（check-i18n 本地 + 线上）
  • 生产环境：/zh/admin 等既有后台功能不受影响
